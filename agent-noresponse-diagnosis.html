🔍 Agent 无响应诊断

场景：用户上传 Word 文档 → 要求「梳理 + 提炼总结 + 生成 HTML」→ 模型调用 filesystem / shell 后无任何回答
STEP 1
用户请求
上传 .docx（5,627 字符）
要求提炼并生成 HTML
→
STEP 2
模型发起工具调用
filesystem read
shell 检查 mammoth
→
STEP 3
工具执行断裂
文件读不到 / 环境无库
执行失败
→
STEP 4
结果未回填
模型等不到工具结果
循环无出口
→
RESULT
模型无响应 ❌
无最终总结 / 无 HTML

缺的东西（技能 / 方法）6 项缺口

① 文档解析技能缺失
表现：模型现场用 shell 试探 mammoth / python-docx
后果：环境无库 → 命令报错 → 卡死
正确做法：应用内置 docx→HTML 转换器（mammoth）或 docx→文本提取（python-docx），上传时同步解析，模型拿到的是纯文本，无需自行试错
② 工具执行引擎缺失
表现：只看到「调用工具」记录，没有执行结果
后果：模型发出 tool_call 后无人执行、结果不回流
正确做法：工具注册表 + 真实执行器 + 结果回填（tool_result 必须发回模型，且带错误信息而非静默失败）
③ 文件访问授权缺失
表现：读 C:\Users\ASUS-BOOK\AppData\Local\Temp\TencentFiles\... 临时目录
后果：沙箱外/权限不足 → 读取失败
正确做法：明确可读目录白名单；文件先经应用层读取再喂给模型，不把文件系统裸交给模型
④ 循环控制缺失
表现：工具调用没有步数 / 超时上限
后果：失败→重试→再失败，死循环或挂起，永不输出
正确做法：max_steps（如 10 步）、单工具超时（如 30s）、失败 N 次强制转文本回传并结束
⑤ Agent 系统提示缺失
表现：模型不知道处理 docx 的正确流程，乱试
后果：工具选择错误 → 无效调用链
正确做法：system prompt 定义工作流：「读取内容 → 结构化提炼 → 输出 HTML」；明确哪些工具可用、最终必须给用户可见答案
⑥ 模型 function calling 能力不匹配
表现：agnes 等 OpenAI 兼容接口对 tools 支持有限
后果：tool_call 被忽略或格式不兼容 → 无响应
正确做法：探测模型是否支持 tools；不支持时回退「纯文本对话 + 应用侧预解析」，不让模型承担工具职责

✅ 颤翎子客户端如何规避这个问题（已内置）

1. 上传 / 拖拽 / 粘贴时，后端立即解析文档（files/upload：docx / xlsx / pptx / pdf / txt / md → 提取文本，卡片显示 5,627 字符即解析结果）；
2. 发给模型的只是纯文本，模型不需要调用任何工具即可完成「梳理 → 提炼 → 生成 HTML」；
3. 无工具依赖 → 无文件权限问题 → 无循环控制问题 → 模型必然给出回答，不会出现截图中的无响应。
结论：把「文档处理」从模型侧（工具调用）上移到应用侧（预解析），是这类场景最稳的架构。
