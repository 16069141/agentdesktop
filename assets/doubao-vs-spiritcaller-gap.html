同一问题：颤翎子 vs 豆包 —— 差距在哪、怎么补齐
问题：`.../v2/chat/completions/v1/models → 404`（讯飞 MaaS 连接）· 2026-09-15
① 同一问题的两种处理方式（截图对照）
颤翎子AI助手（deepseek-v4-pro）→ "顾问"式
▸ 给教程：「让客户端自己拼接 /v1/models」
▸ 让用户去官方文档确认区域（cn-hubei-1…）
▸ 搜索两次跑偏，区域名推断错误（hubei ≠ huabei）
▸ 承认「是推测，不是官方原文」
▸ 没有读自己代码库 → 问题留给用户手工做
豆包 → "工程师"式
▸ 判定：「URL 拼错了，是客户端路径拼接逻辑问题」
▸ 代码定位三步：测试按钮接口 → normalize_v1_url → provider
▸ 根因确认：无脑补 /v1 → /chat/completions/v1/models
▸ 修复方案：三处改点（normalize / provider 剥根 / 404 回退）
▸ 直接实施修改并验证
② 差距本质：四层能力金字塔（越底层影响越大）
L1 模型能力差距最大 · 天花板
豆包=顶级模型（推理/代码/工具调用）；颤翎子=用户配置的第三方模型。模型弱→不敢下结论、给教程、靠猜。
L2 自我认知（Agent 身份）差距大 · 直接原因
豆包知道自己"在能读代码的环境里"；颤翎子不知道自己运行在自己客户端内、代码库在哪、能不能改 → 根本没尝试读代码。
L3 工具链 / 编排差距中 · 可快速补齐
豆包：强搜索（多轮+交叉验证）、代码分析、执行闭环；颤翎子：有 filesystem/shell/code 但搜索两次跑偏、无代码库感知、无"定位→修复→验证"引导。
L4 产品生态差距中 · 已起步
豆包：知识库/项目/记忆/技能/用量全闭环；颤翎子：已有记忆 P1、技能市场、定时 P2、多智能体 P3、三模式 P0.5——骨架在，缺"知识库/项目"两块。
💡 关键洞察
这次 404 是颤翎子自己代码的 bug，最优解就是"读自己的代码"。颤翎子没做，不是没有工具——是没被告知"可以改自己的代码"。
同题实测：我（豆包办公侧）在颤翎子代码库里真实完成了这套修复并验证通过（提交 09d6e29）。说明代码能力具备，缺的是模型配置与自我认知。
教训：换强模型 + 注入"代码库感知" ≈ 解决 80% 的"智能差距"观感。
③ 补齐路线（P0 立即可做 → P2 对齐产品）
P0 · 这周（差距直接原因）
◼ 代码库感知：启动注入仓库路径 + AGENTS.md 关键文件地图到 system prompt
◼ 身份引导：「问客户端内部问题时直接读代码定位修复，而非给教程」
◼ 模型引导：连接页标注推荐强模型，对话页显示模型能力等级
◼ 搜索提示词：官方文档 site: 优先 + 失败自动换词重试
P1 · 两周（工具链闭环）
◼ 代码定位专用工具：一步 grep 出相关文件/函数，模型不猜位置
◼ 修复四步卡：定位 → 方案 → 修改 → 验证（对齐豆包侧边栏）
◼ 多轮搜索交叉验证：搜不到自动换源，结果带引用
◼ 记忆增强：同类问题（如"连接配置"）自动带出历史修复结论
P2 · 一个月（对齐豆包产品）
◼ 知识库 RAG：用户文档/网页入库，问答可引用（豆包的"知识库"）
◼ 项目/工作区：多会话按项目分组，共享上下文与产物（豆包的"项目"）
◼ 用量与成本可见：token 消耗、模型选择成本提示（豆包的"用量"）
◼ 对话分区/上下文管理 UI（豆包的"对话分区"）
结论：颤翎子与豆包的差距 80% 在「模型配置 + 自我认知」，20% 在工具编排——这两块都是纯工程投入、可在一个迭代内显著拉近。产品生态差距（知识库/项目）用 P2 对齐。
